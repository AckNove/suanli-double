## 0. 设计原则

1. **低成本、可替换、易维护**：本地优先，无云服务器阶段也能跑。  
2. **工具层共享，业务数据隔离**。  
3. **先证据与工作流，后智能体花活**。  
4. **每个外部调用可日志、可失败降级**。

---

| 项 | 建议 | 状态 |

| 默认 LLM | DeepSeek（Harness 已具备） | **需本地接线** |

---

## 2. 网络搜索层

```
QueryPlanner → SearchProvider → Rank/Dedup → FetchQueue
```

- Provider：可插拔（SerpAPI / Bing / 本地浏览器 / 本 Bot 的 WebSearch 能力作原型）  
- 必须保存：query、时间、命中 URL 列表  
- 失败：标记 `search_failed`，不伪造结果  

**当前已验证能力**：Grok Bot 侧 WebSearch/WebFetch（用于本交接包研究）。  
**产品内搜索服务**：未开发。

---

## 3. 网页读取层

- HTML → 正文提取（trafilatura/readability 类）  
- 反爬/403：记录状态码，换源，不编造正文  
- 动态页：后期 Playwright（可选，成本高则人工粘贴）

---

## 4. PDF / Word / Excel 解析层

| 格式 | 建议库 | 状态 |
|------|--------|------|
| PDF | pymupdf / pdfplumber；扫描件后期 OCR | **需本地** |
| DOCX | python-docx | **需本地** |
| XLSX | openpyxl / pandas | **需本地** |

输出统一为 `RawDocument`：文本块、页码、表格 JSON、文件哈希。

---

## 5. 原始资料存储

```
data/
  raw/{project}/{yyyy}/{mm}/{doc_id}/
    source.bin / source.pdf
    meta.json      # url, retrieved_at, content_type, hash
  text/{doc_id}.md
```

Git **不**提交大二进制；用 Git-LFS 或本地盘。私密商务附件进 `data/private/`（gitignore）。

---

## 6. 证据管理

表 `evidence_claims`（逻辑字段同证据表）：  
claim_id, project_id, statement, epistemic_tag(fact|inference|hypothesis|missing),  
source_name, url, published_at, retrieved_at_shanghai, excerpt,  
source_type, trust_level, verification_status, conflict_notes, doc_id

规则：  
- 报告中引用必须 `[@claim_id]`  
- 状态机：`unverified → cross_checked → disputed → rejected`

---

## 7. 结构化知识库

**共享（A↔B 可读）**  
- 公开公司、产业链节点、政策摘要、公开产品  

**隔离（仅 B 或仅 A 会员）**  
- B：contacts, quotes, contracts, outreach  
- A：付费会员 PII、订阅状态  

实现建议：同一 Postgres 不同 schema + 应用层强制；或两个 SQLite 文件。  
**平台 Bot 无 ACL → 隔离必须在自建系统实现。**

轻量图谱：`nodes(companies, segments)` + `edges(relation_type, evidence_id)`。

---

## 8. 产业链与公司关系管理

- 关系必须挂 `evidence_id`；无证据不得写「已确认供应关系」  
- 变更记版本；冲突关系并存并标 `disputed`

## 9. 智能体如何调用工具

统一 `ToolRouter`：

| 工具 | 输入 | 输出 |
|------|------|------|
| search | query | hits[] |
| fetch | url | text, status |
| parse_file | path | RawDocument |
| evidence_add | claim | claim_id |
| kb_upsert | entity | id |
| match_suppliers | demand | matches[]（仅B） |

Bot 层（Grok）与本地 Harness 智能体应对齐同一份工具契约（JSON schema）。

## 10. 研究任务如何分配

```
Orchestrator 建 ResearchTicket
  → 分解 ResearchQuestion[]
  → 派 Search / Fetch / Extract
  → 派 Analyst 角色（可先单 agent 多 prompt）
  → Verifier 抽检
  → Writer 出报告
```

Grok 侧：群内派活 + SendToAgent。  
本地侧：队列（RQ/Celery 或先用文件系统 inbox）。

---

## 11. 交叉验证

1. 重要数字 ≥2 独立来源或 1 官方 + 1 行业  
2. 冲突写入 `conflict_notes`，禁止静默覆盖  
3. 抽样人工复核清单（每篇报告至少 3 条）

---

## 12. 质量评测

自动：  
- 断链率、无摘录结论占比、epistemic 标签缺失率  
人工：  
- 准确性抽检、是否夸大、是否把推断当事实  

评分写入 `qa_reviews`；不达标不得标「可对外」。

---

## 13. 任务调度

- 短期：cron / Harness 手动  
- 中期：追踪任务表 `tracking_items`（财报日、政策意见截止日等）  
- Routine（Grok）：可选，**当前未创建**

---

## 14. 数据权限管理（必须自建）

| 级别 | 内容 | 访问 |
|------|------|------|
| L0 公开研究 | 已发表报告摘要 | A/B 研究角色 |
| L1 内部研究 | 未发布证据与草稿 | 项目内 |
| L2 商务敏感 | 联系人、报价、合同 | 仅 Arthur + 明示授权 agent |
| L3 密钥 | API Key | 仅本地环境变量 |

导出 L2 必须记审计日志。

---

## 15. 日志与失败处理

- 结构化日志：request_id, tool, latency, error  
- 失败分类：network / parse / policy_block / budget  
- 降级：跳过该源、标记缺口、继续其他问题（符合用户研究工作流第失败条款）
